# Chain-of-Thought: оформление заказа

Задача: провести человека от выбранного набора до статуса «Оплачен», не потеряв адрес на экране входа и не списав деньги по завтрашней дате.

Задача разрезана на три шага. Следующий шаг начинается с результата предыдущего.

## Шаг 1. Правила, которые не зависят от экрана

Промпт:

```markdown
Role: Ты разработчик доменных правил.
Task: Опиши проверки заказа так, чтобы их вызвали и форма, и сервер.
Context: Календарь Europe/Moscow. Первая доставка не раньше чем через 2 календарных дня. Город только Москва. Интервалы 10-14, 14-18, 18-22. Телефон +7 и 10 цифр с 9. Цена берётся из набора, не из умножения.
Format: Список функций и таблица «вход → отказ». Без React.
```

Результат шага: `src/lib/domain.ts` (`parseOrderInput`, `earliestDeliveryDate`, `inspectCard`) и тесты в `src/lib/domain.test.ts`. Вечер 14 октября 21:30 UTC считается 15 октября в Москве, ближайшая доставка — 17 октября.

## Шаг 2. Контракт API

Промпт:

```markdown
Role: Ты проектируешь HTTP API по готовым правилам.
Task: Зафиксируй создание заказа, оплату и чтение чужого заказа.
Context: Правила из шага 1 уже есть. Сессии нет — 401. Заказ чужой — 403. Заказа нет — 404. Отказ банка — 402. Ошибка поля — 400 и словарь fields. Полный номер карты в базу не пишется.
Format: Таблица метод, путь, код ответа. Одна форма ошибки на все поля.
```

Результат шага: маршруты `POST /api/orders`, `POST /api/payments`, `GET /api/orders/:id`. Общий контракт `validation_error` описан требованием 45 в `technical_specification.md`. Оптимизация «один словарь fields вместо отдельной формы на каждое поле» не отменяет правила даты и карты.

## Шаг 3. Состояния экрана

Промпт:

```markdown
Role: Ты собираешь экран оформления.
Task: Покажи, что видит человек без сессии, с ошибкой даты и после сохранения заказа.
Context: Контракт шага 2. Черновик адреса надо сохранить до входа. После входа человек возвращается на тот же набор.
Format: Список состояний: загрузка, ошибка сети с «Повторить», ошибки полей, успех с переходом на оплату. Без новых полей, которых нет в контракте.
```

Результат шага: `CheckoutScreen` пишет черновик в `localStorage`, при отсутствии сессии ведёт на `/login?next=/checkout?plan=...`, серверные `fields` рисуются под полями. Оплата живёт отдельным экраном и не смешана с адресом.

Проверка цепочки: интеграционный тест создаёт заказ на неделю за 5 490 ₽, чужому пользователю отдаёт 403, карта 4000000000000002 даёт 402, карта 4242 переводит заказ в «Оплачен», отметка получения ставит «Доставлен».
