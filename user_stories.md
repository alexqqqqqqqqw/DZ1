# Карта историй MVP «Норма»

Путь описан в [user_journey.md](user_journey.md). Истории ниже покрывают этот путь. Приоритет: Must — входит в MVP, Should — следом, Nice — не делается в этой версии.

Роли: новый пользователь, пользователь с аккаунтом.

## 1. Открытие сервиса

Приоритет: Must. Этап: Обнаружение и первая точка входа.

Я как новый пользователь, хочу увидеть на первом экране состав заказа и минимальную цену дня, чтобы решить, открывать ли каталог.

Критерии приемки:

- Given сервис открыт и каталог из 4 типов доступен, When пользователь смотрит первый экран, Then видны текст про готовые наборы, срок в 2 дня, доставку по Москве и цена «Дневной набор от … ₽».
- Given запрос типов питания не ответил, When первый экран загрузился, Then вместо цены показан текст «Цену дня покажем в каталоге, если сервер ответит.» и кнопки перехода остаются на месте.
- Given каталог отвечает, When измеряется время ответа `GET /api/diets` на локальной базе, Then ответ содержит ровно 4 типа и приходит не дольше 2 секунд.

## 2. Онбординг

Приоритет: Must. Этап: Разрешение на уведомления и онбординг.

Я как новый пользователь, хочу прочитать три коротких экрана о заказе, чтобы не гадать, можно ли собрать тарелку самому.

Критерии приемки:

- Given пользователь нажал «Выбрать тип питания» и онбординг ещё не завершён, When открывается онбординг, Then первый экран говорит, что блюда внутри набора не меняются.
- Given пользователь на втором экране, When он нажимает «Дальше», Then виден экран про оплату до перехода к уведомлениям.
- Given онбординг завершён, When пользователь снова открывает первый экран и нажимает «Выбрать тип питания», Then он попадает в каталог, а не на онбординг.

## 3. Уведомления о доставке

Приоритет: Must. Этап: Разрешение на уведомления и онбординг.

Я как новый пользователь, хочу разрешить или пропустить уведомление, чтобы не потерять заказ из-за отказа браузера.

Критерии приемки:

- Given показан шаг уведомлений и браузер умеет `Notification`, When пользователь нажимает «Разрешить уведомления» и браузер возвращает granted, Then в локальном хранилище записано `granted` и открыт каталог.
- Given браузер вернул denied или пользователь нажал «Не сейчас», When шаг завершается, Then записано `denied` или `skipped` и каталог всё равно открыт.
- Given у браузера нет API уведомлений, When пользователь нажимает «Разрешить уведомления», Then записано `skipped` и показана фраза, что статус останется в заказах.

## 4. Выбор типа питания

Приоритет: Must. Этап: Выбор типа питания.

Я как пользователь, хочу выбрать один из четырёх типов, чтобы видеть только его день и неделю.

Критерии приемки:

- Given каталог загружен, When пользователь открывает «Рационы», Then показаны ровно 4 типа: Сбалансированный, Высокобелковый, Вегетарианский, Низкоуглеводный, у каждого диапазон калорий и цена «от».
- Given выбран тип, When список наборов обновляется, Then видны только наборы этого типа: один на 1 день и один на 7 дней.
- Given описание вегетарианского типа, When пользователь его читает, Then указано, что мяса и рыбы нет, а яйца и молочные продукты есть, и отдельного веганского набора нет.
- Given в параметр `diet` передана строка `balanced' OR '1'='1`, When запрашивается список наборов, Then результат пустой.

## 5. Меню и КБЖУ

Приоритет: Must. Этап: Детальный просмотр меню.

Я как пользователь, хочу открыть состав дня с калориями, белками, жирами и углеводами, чтобы решить, брать ли набор.

Критерии приемки:

- Given открыт набор, When пользователь смотрит день, Then у каждого приёма есть название, описание, ккал, белки, жиры и углеводы.
- Given набор на 7 дней, When пользователь нажимает «День 3», Then показаны 4 блюда третьего дня, а не первого.
- Given набор на 1 день, When меню открыто, Then переключателя дней нет и показан единственный день.
- Given карточка набора, When пользователь читает цену, Then сумма равна цене этой записи каталога. Цена недели не вычисляется умножением дневной цены на 7.
- Given идентификатор набора не существует, When открывается меню, Then ответ API 404 с сообщением «Набор не найден.»

## 6. Дата, интервал и адрес

Приоритет: Must. Этапы: Выбор длительности и даты первой доставки; Адрес и интервал доставки.

Я как пользователь, хочу указать дату не раньше чем через 2 дня, интервал и адрес в Москве, чтобы партнёр привёз набор.

Критерии приемки:

- Given сейчас календарная дата D в зоне Europe/Moscow, When пользователь отправляет дату раньше D+2, Then заказ не создаётся, HTTP 400, в `fields.startDate` есть дата D+2.
- Given дата равна D+2 или позже, When остальные поля верны, Then дата принимается.
- Given поле интервала, When пользователь выбирает значение, Then доступны только `10-14`, `14-18`, `18-22` с подписями 10:00–14:00, 14:00–18:00, 18:00–22:00.
- Given город не «Москва», When заказ отправляется, Then HTTP 400 и `fields.city` сообщает, что доставка только по Москве.
- Given улица короче 2 символов, дом пустой или телефон не мобильный +7 9XXXXXXXXX, When заказ отправляется, Then HTTP 400 и ошибка стоит у соответствующего поля.
- Given поля верны, When заказ создан, Then статус «Ждёт оплаты», а `totalKopecks` равен `price_kopecks` выбранного набора на этот момент.
- Given на экране оформления, When пользователь читает сумму, Then отдельно написано, что доставка по Москве входит в цену набора.

## 7. Регистрация

Приоритет: Must. Этап: Регистрация и вход.

Я как новый пользователь, хочу создать аккаунт по почте и паролю, чтобы заказ сохранился на меня.

Критерии приемки:

- Given имя от 2 до 80 символов, почта в формате name@example.com, пароль от 8 до 72 символов с буквой и цифрой и мобильный телефон, When пользователь регистрируется, Then ответ 201, в нём нет хеша пароля, и сессия уже открыта.
- Given пароль короче 8 символов или без цифры, When регистрация отправляется, Then HTTP 400 и текст в `fields.password`.
- Given почта уже занята, When регистрация отправляется, Then HTTP 409 и `fields.email` предлагает войти.
- Given пользователь создан, When смотрят таблицу `users`, Then в `password_hash` лежит bcrypt-хеш с cost factor 10, а исходного пароля в таблице нет.

## 8. Вход и сессия

Приоритет: Must. Этап: Регистрация и вход.

Я как пользователь с аккаунтом, хочу войти и оставаться в сессии 7 дней, чтобы не вводить пароль на каждом экране.

Критерии приемки:

- Given верные почта и пароль, When пользователь входит, Then ответ 200 и cookie `norma_session` имеет HttpOnly, SameSite=Lax и срок 7 суток.
- Given почта неизвестна или пароль неверный, When пользователь входит, Then HTTP 401 и одно сообщение «Неверная почта или пароль.»
- Given пользователь на оформлении без сессии и черновик адреса заполнен, When он нажимает «Войти и продолжить» и успешно входит, Then он возвращается на оформление, а улица и дом на месте.
- Given сессия есть, When пользователь нажимает «Выйти», Then следующий `GET /api/auth/me` возвращает `user: null`.

## 9. Оплата

Приоритет: Must. Этап: Оплата заказа.

Я как пользователь, хочу оплатить заказ картой и увидеть отказ или успех, чтобы понять, ушёл ли набор в готовку.

Критерии приемки:

- Given заказ в статусе «Ждёт оплаты» или «Оплата не прошла», номер из 16 цифр проходит проверку Луна, срок не раньше текущего месяца по Москве, CVV из 3 цифр и номер не равен 4000000000000002, When пользователь платит, Then статус становится «Оплачен», в `payments` пишется `succeeded` и `last4`.
- Given номер 4000000000000002 и остальные поля карты верны, When пользователь платит, Then HTTP 402, сообщение «Банк отклонил карту. Заказ не оплачен.», статус «Оплата не прошла».
- Given номер не проходит Луна, срок прошёл или CVV не из 3 цифр, When пользователь платит, Then HTTP 400, заказ остаётся в прежнем статусе, запись платежа не создаётся.
- Given заказ уже «Оплачен» или «Доставлен», When пользователь платит снова, Then HTTP 409 и вторая успешная оплата не создаётся.
- Given оплата прошла, When смотрят столбцы `payments`, Then среди них нет `number`, `pan` и `cvv`. В строке хранится 4 цифры.

## 10. Свой заказ

Приоритет: Must. Этап: Подтверждение заказа.

Я как пользователь, хочу открыть список и карточку своих заказов, чтобы сверить дату, адрес и статус.

Критерии приемки:

- Given у пользователя есть заказы, When он открывает «Заказы», Then видны название набора, дата, интервал, статус и сумма, новые заказы выше.
- Given заказов нет, When он открывает «Заказы», Then показано пустое состояние «Заказов нет», а не сообщение об ошибке.
- Given пользователь не вошёл, When он запрашивает `GET /api/orders`, Then HTTP 401 и сообщение «Войдите, чтобы продолжить.»
- Given заказ принадлежит другому пользователю, When запрошен `GET /api/orders/{id}`, Then HTTP 403 и сообщение «Этот заказ принадлежит другому аккаунту.»
- Given такого заказа нет, When запрошен `GET /api/orders/{id}`, Then HTTP 404.
- Given роль `norma_app` выполняет `SELECT` из `orders` без `app.user_id`, When запрос завершается, Then число строк равно 0, даже если заказы в таблице есть.

## 11. Получение набора

Приоритет: Must. Этап: Получение набора.

Я как пользователь, хочу отметить оплаченный заказ полученным, чтобы в истории стоял статус «Доставлен».

Критерии приемки:

- Given статус «Оплачен», When пользователь нажимает «Я получил набор», Then статус становится «Доставлен».
- Given статус «Ждёт оплаты» или «Оплата не прошла», When приходит запрос отметки, Then HTTP 409 и статус не меняется.
- Given статус уже «Доставлен», When отметка приходит снова, Then HTTP 409 и сообщение «Заказ уже отмечен полученным.»

## 12. Сбой сети и единый ответ об ошибке полей

Приоритет: Must. Этапы: все экраны с загрузкой данных.

Я как пользователь, хочу увидеть сбой сети отдельно от ошибки в поле, чтобы понять, повторять запрос или исправлять ввод.

Критерии приемки:

- Given каталог или список заказов не достучался до сервера, When экран обработал сбой, Then виден текст «Нет связи с сервером. Проверьте сеть и повторите.» и кнопка «Повторить».
- Given регистрация, заказ или карта не прошли проверку, When API отвечает, Then HTTP 400, `error.code` равен `validation_error`, есть `error.message` и словарь `error.fields` с ключом поля.
- Given сервер поймал необработанное исключение, When запрос завершается, Then HTTP 500, код `internal_error` и сообщение «Сервер не смог обработать запрос. Повторите через минуту.»
- Given любой из запросов регистрации, входа, выхода, заказа, оплаты и отказа доступа, When операция записана, Then в журнале есть JSON-строка с полями `ts`, `level`, `event`. В этой строке нет пароля и полного номера карты.

## 13. Проверка живости и чужой origin

Приоритет: Should. Этап: Подтверждение заказа.

Я как дежурный по стенду, хочу открыть проверку живости и не отдать API чужому сайту, чтобы понять, жива ли база, и не пустить чужой origin к cookie.

Критерии приемки:

- Given в базе 4 типа питания, When запрошен `GET /api/health`, Then HTTP 200, `status` равен `ok`, `db` равен `up`, `diets` равен 4.
- Given каталог пуст, When запрошен `GET /api/health`, Then HTTP 503 и `status` равен `degraded`.
- Given браузер прислал `Origin: http://127.0.0.1:38471` на `/api`, When сервер отвечает, Then заголовок `Access-Control-Allow-Origin` равен этому origin.
- Given origin другой, When сервер отвечает на `/api`, Then заголовок `Access-Control-Allow-Origin` не выставляется.

## 14. Фото блюд

Приоритет: Nice. Этап: Детальный просмотр меню.

Я как пользователь, хочу видеть фото блюда с кухни, чтобы узнать порцию до заказа.

Критерии приемки:

- Given эта история в приоритете Nice, When собирается MVP, Then фото блюд нет и история не входит в требования реализации.
